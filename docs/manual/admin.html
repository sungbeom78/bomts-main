로컬 개발

공개 소스를 실행하고 검사하는 재현 가능한 최소 절차입니다.

DEV
이 장은 기여자가 자신의 개발 환경에서 사이트를 확인하는 방법을 다룹니다. Production 배포와 운영자 권한이 필요한 절차는 포함하지 않습니다.

로컬 실행 · 1 / 2

예제 환경값으로 로컬 사이트를 실행합니다

localdevelopment
cp .env.example .env
docker compose up --build
curl -fsS http://127.0.0.1:8080/healthz
health endpoint returns: ok
개발 포트가 사용 중이면 ignored .env의 BOMTS_HTTP_PORT를 바꿉니다.
예제 환경 파일은 로컬 개발 기본값만 포함합니다. Compose로 정적 사이트를 실행한 뒤 health endpoint가 응답하는지 확인합니다. Production 환경값과 주소는 이 저장소에 기록하지 않습니다.

로컬 실행 · 2 / 2

변경 후 공개 저장소 검사를 실행합니다

  1. 콘텐츠페이지·링크 확인
  2. 구성Compose 검증
  3. 정책보호 구역 확인
  4. 매뉴얼렌더링 확인
  5. 보안Secret 검사
repositoryverification
./scripts/check.sh
python .claude/skills/sk-mgm-task-state/scripts/run.py protect-check
사이트 변경 뒤에는 프로젝트 검사와 보호 구역 검사를 실행합니다. 새 기능이나 사용법이 바뀌면 공개 매뉴얼도 함께 고치고 렌더링 결과를 확인합니다. Public release 전에는 현재 트리와 전체 이력을 별도 Secret scanner로 검사합니다.

책임 경계

공개 개발과 Production 운영 책임을 분리합니다

Public 저장소

  • 제품 소스와 공개 문구
  • 일반화한 로컬 실행
  • 논리 아키텍처
  • 비밀 없는 검사

Private 인프라

  • 실제 호스트와 네트워크
  • 배포·백업·복구
  • 메일·방화벽·모니터링
  • 운영 evidence
Production 변경은 Private runbook과 별도 승인 절차를 따릅니다.
Public 저장소는 제품을 이해하고 로컬에서 검증하는 데 필요한 내용만 제공합니다. 실제 운영 환경을 재현할 수 있는 상세 정보는 Private 인프라 저장소에 둡니다. 이 경계는 Secret 유무와 별개로 공격 표면을 줄이기 위한 원칙입니다.
